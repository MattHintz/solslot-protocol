# Solslot V2 Official Testnet11 Genesis Runbook

## Controlling release

This runbook controls the official Testnet11 path for:

- release ID `solslot-v2-alpha-rc27.35-20260823`;
- branch `release/testnet-alpha-rc27.35-20260823`; and
- the exact nine-source manifest generated by the frozen Protocol tooling.

The frozen API repository's `GENESIS_README.md` and `ADMIN_README.md` control
the coordinator endpoints and authorization boundaries. If either document,
the source manifest, or the deployed API disagrees with this runbook, stop.
Do not select whichever instruction is less restrictive.

The `V2`, `V3`, `V4`, `RC23`, and `RC27` strings in schema and puzzle names are
compatibility identifiers. They do not authorize an older release, state tree,
review policy, or ceremony.

## Safety and authorization boundary

Genesis is a sequence of separately authorized irreversible phases. Approval
to freeze, back up, configure, deploy, or smoke-test a closed service does not
authorize an owner claim, ceremony row, enrollment, plan, funding, signature,
gate activation, broadcast, finalization, customer write, purchase, or mint.

Before each mutating phase, record a new ActionEnvelope naming the exact
release, environment, allowed endpoint or action, stop point, compliance
flags, and rollback or reconciliation rule. The first initialization envelope
should authorize exactly one guided owner claim and then stop.

No step in this runbook authorizes production or mainnet. Network remains Chia
Testnet11 and Ethereum Sepolia, and every artifact remains `testOnly: true`.
Existing contracts, launchers, vaults, proofs, bridge coins, manifests,
browser state, ceremony databases, and output directories are retired and
must not be reused.

## Official Testnet11 policy

1. The official guided flow uses the protected server review class
   `independent-release-review`; browser input cannot select or downgrade it.
2. An owner claim may resume an active ceremony only when its protected
   canonical draft exactly matches the current release policy. A mismatch
   returns a conflict without consuming the one-time claim.
3. Fresh Sepolia identity-contract deployment evidence must exist before the
   plan is built and must be reverified against live code at strict preflight.
4. Independent approval is bound to the exact approved plan, becomes blocking
   after owner-plus-one plan approval, and is revalidated at strict preflight.
5. `internal-engineering-testnet` is a server-selected disposable workflow
   only and must never be represented as the official genesis.
6. Base Sepolia payment ownership and Stripe rehearsal do not block genesis,
   but presale and purchase activation stay locked until their separate
   post-genesis gates pass.

## Phase 0: freeze and closed staging preparation

Freeze these nine canonical repositories at their exact live `main` commits:

- Protocol;
- EVM;
- Omnichain;
- API;
- legacy backend/payment adapter;
- Key of Solomon;
- Samuel;
- customer web; and
- admin portal.

For every repository, create the coordinated release branch and an annotated
release tag without force. Verify that live `main`, the live release branch,
the annotated tag's peeled commit, the local tracking refs, and the exact
local/remote tag object all bind to the same reviewed commit. An absent,
lightweight, moved, malformed, duplicate, unexpected, or divergent ref is a
release failure. Never delete or retarget a published release ref; increment
the release ID instead.

From unique clean canonical checkouts on the release branch, generate the
manifest and source evidence with the frozen Protocol tool:

```bash
.venv/bin/python scripts/build_release_source_manifest.py \
  --protocol-repo /release/solslot-protocol \
  --evm-repo /release/solslot-evm \
  --omnichain-repo /release/omnichain \
  --api-repo /release/solslot-api \

  --customer-web-repo /release/solslot \

  --output /secure/ceremony/source-manifest-rc27.35.json \
  --evidence-output /secure/ceremony/source-freeze-evidence-rc27.35.json \
  --require-release-refs
```

Verify the manifest independently with the release coordinator and seal the
new checksum index. Do not copy an RC27.33 approval or readiness receipt into
RC27.35. Source evidence must keep independent review, fresh funding,
ceremony-package, settlement, and administrator-enrollment readiness false
until each fact is proven for this release.

Before deployment, a reviewer outside the implementation team must complete
the pre-deployment source-scope review for the exact RC27.35 commits and record
the disposition of every finding. Regenerate the request after any source-
commitment change. This source review is not the later Authority V3 live-
deployment receipt, plan-bound approval, or post-deployment addendum and
cannot substitute for any of them.

An unresolved high-severity finding is a stop condition and cannot be
dispositioned as approval or included in a finalized review receipt.

The independent RC27.35 protocol review records unresolved Medium
`M-ANN-INJECT`. It is accepted only for Testnet11 preparation because it
requires the same two daily keys and recovery key as the honest lost-key path
and is not constructed by the reviewed canonical drivers. Operators must use
only those drivers, keep recovery keys offline and separated, and reject or
alert on a reserved `0x5303` announcement outside the canonical lost-key
preparation path. This disposition authorizes no mainnet, real assets, legal
rights, customer funding, ceremony, signature, or broadcast. The finding must
be remediated and independently reviewed before any mainnet or real-value
release.

Before deploying RC27.35 to staging:

1. complete the RC27.35 credential carryover record, including provider-side
   revocation and replacement evidence for the credential found in public
   history, generate signer 1/2 and private-network material, and separately
   provision the owner-claim, launch-session, and direct-operator credentials;
2. have two operators verify the public signer, certificate, and private-

5. configure the exact manifest and source-evidence hash;
6. set both repository and staging-environment Protocol pins to the same

7. keep ceremony mode, customer writes, minting, workers, purchase, payment,

8. require a 15-minute closed health gate with a loopback listener, the local

Stop after this phase. It is not initialization.

## Phase 1: one guided owner claim

This phase requires two separately enumerated authorization scopes. First, an
isolated-process envelope must authorize only the temporary ceremony ceiling:
`SOLSLOT_CEREMONY_MODE_ENABLED=true`,
`SOLSLOT_ALPHA_WRITES_ENABLED=true`, and guided launch control enabled on the
loopback-only Testnet11 ceremony process. Minting, workers, payment ownership,
purchase, presale, settlement, KoS signing, metadata mutation, and every other
write surface and public customer routing remain disabled. These flags are
server ceilings only; they authorize no funding, signature, gate, or
broadcast. Startup must fail for any different posture. Prove the process
healthy and zero-ceremony, then stop.

Second, a distinct initialization envelope must authorize exactly one guided
owner claim and then stop. Neither scope authorizes enrollment, plan creation,
funding, signature, gate approval, broadcast, finalization, or customer writes.

The official flow starts only through the server-generated single-use guided
owner claim. The browser receives the claim in the URL fragment. The launch
session is transported only as a protected `HttpOnly`, `Secure`, `SameSite`
cookie and must not enter script-readable storage. The ceremony operator token
remains server-only. The browser does not submit `reviewClass` or release
identity. No claim, cookie, operator token, or enrollment token belongs in
logs, evidence, chat, or source control.

The direct `POST /admin/genesis/drafts` surface is a protected compatibility
workflow, not the official path and not a readiness bypass. Do not use it
unless a separate envelope explicitly names that compatibility workflow.

Before exposing the claim endpoint, the approved initialization preflight must
establish the exact RC27.35 manifest, configured source-evidence path and hash,
reviewed plan-template path, Testnet11 policy, and protected
`independent-release-review` class. The claim transition checksum-validates the
release evidence and atomically creates or resumes only an exact canonical
protected draft; it does not validate or approve the later plan. A canonical-
draft mismatch or conflict must leave the claim unconsumed and make no ceremony
mutation. If the HTTP result is missing, timed out, or ambiguous, do not retry
and do not assume the claim remains unconsumed; stop and reconcile the server-
side claim-use record and active ceremony ledger using read-only evidence.

The successful claim response contains a secret `ownerEnrollmentToken` and a
protected session cookie. Do not archive either. Record only the non-secret
`ceremonyId`, then stop. Invitation acceptance and administrator enrollment
are later authorization phases.

## Phase 2: enrollment and plan construction

Use separate ActionEnvelopes for fresh Sepolia deployment; administrator
invitations, enrollment, and recovery drills; roster freeze; Chia funding
fan-out and confirmation; plan construction; plan-signature submissions;
Authority V3 roster export and Base Sepolia governance deployment; review-
receipt installation; gate proposal, signature, and activation; broadcast;
confirmation; artifact signatures; and finalization. Authorization for one
group authorizes no other group.

Required roles are three distinct administrator identities, three validators
on separately controlled signer hosts, two validator signatures per
credential stamp, owner-plus-one administrator approval for the plan and
public artifact, and an independent reviewer outside the implementation team
for the official release.

Before building the plan:

- complete the credential record and two-operator public-fingerprint check;
- prove all three validators healthy over their private authenticated network;
- deploy fresh reviewed Sepolia identity contracts from the exact frozen EVM
  source, record addresses, transactions, bytecode hashes, and source SHAs,
  and wait for at least 12 confirmations;
- select fresh confirmed unspent Chia funding coins through the synced local
  primary node; and
- prove the ceremony output directory and every designated finalization target
  remain absent. The isolated ceremony database created by the guided claim is
  expected to contain the authorized ceremony row; do not describe it as
  empty, delete it, recreate it, or substitute it.

Enroll administrators only through their own trusted devices and complete
their separate recovery drills. Freeze the roster and construct the
deterministic plan. The plan must bind all source commits, the nine fixed
ceremony inputs, fresh EVM identities, validator keys, trusted destinations,
retired coordinates, deterministic protocol outputs, and consensus-simulation
commitments. The final fee coin and fee-funded broadcast bundle are not
selected or reserved during plan construction.

After roster freeze and plan construction, export the public Authority V3
roster only with `scripts/export_authority_v3_roster.py`. Never use the legacy
`export_safe_owner_roster.py`, whose schema lacks the required recovery and
Chia launcher bindings. Under separate authorization, deploy the live Base
Sepolia Authority V3 governance contracts and generate governance evidence.
An unresolved high-severity finding is a stop condition and cannot be
dispositioned as approval or included in a finalized review receipt. Finalize
the independent Authority V3 receipt against the exact source commitment and
live deployment. This is distinct from Base Sepolia payment-rail ownership,
which remains nonblocking for genesis.

Then have the owner and one coadministrator independently review and approve
the plan. That approval makes the separate four-lane plan-bound approval a
blocking strict-preflight requirement.

## Phase 3: plan-bound review and strict preflight

After owner-plus-one plan approval, obtain the independent approval bound to
that exact plan, release, consensus-simulation bundle ID, validators, and fresh
Sepolia deployment. All four audit lanes must approve. Do not create a
placeholder approval before the plan exists and do not carry approval across
a plan, source, funding, signer, or contract change.

Strict preflight must independently:

- reconstruct the plan-derived protocol bundle and validate its
  `consensusSimulationBundleId`;
- reread every funding coin from the synced local Testnet11 primary node;
- simulate the full consensus spend;
- revalidate the plan-bound independent approval;
- reload and validate the separate Authority V3 deployment/review receipt;
- reverify live Sepolia code, source identity, transactions, and at least 12
  confirmations;
- probe every validator through authenticated private transport;
- prove the output directory is empty; and
- prove all write and payment gates remain closed except the narrowly
  authorized isolated ceremony ceiling.

Run the Protocol offline `pre-broadcast` verifier against the exact state,
preflight evidence, plan-bound approval, nine canonical release checkouts, and
empty output directory. Both API and offline preflight must be ready
immediately before any broadcast authorization.

## Phase 4: broadcast, confirmation, and finalization

These are separately authorized chain-writing actions. A fresh owner-plus-one
`ceremonyBroadcast` gate authorizes only the exact ceremony and signed window.
Inside the broadcast boundary, the provider selects the fee coin and prepares
the final fee-funded bundle. Before the provider push, the store must
atomically persist the exact bundle bytes and ID, fee coin, plan hash, gate
authorization, and review evidence. The signed gate binds the ceremony and
time window; this durable reservation binds the exact fee-funded bundle. No
preexisting plan-stage bundle may be treated as that reservation.

If the push result is missing, timed out, partial, or ambiguous, stop and
reconcile every reserved input and predicted output through the local primary
node. The only permitted retry is the byte-for-byte reserved bundle under a
fresh valid broadcast gate after reconciliation proves it safe. Never rebuild,
substitute, or blindly replay a bundle.

Require every predicted output to be current with the required Testnet11
confirmations before constructing the public artifact. Obtain owner-plus-one
artifact signatures, finalize once, write checksums, and write the read-only
bootstrap lock last. Never manually edit an artifact, database, lock, bundle,
or checksum file.

After the ceremony archive and checksums are verified, stop the isolated
ceremony process and remove the owner-claim and direct operator-token material.
Do not change normal customer-write posture without separate authorization.

## Phase 5: consumers and smoke gate

Deploy API, customer web, and admin portal from the signed artifact's exact
source commits. Each consumer must report the same artifact hash, Testnet11,
and closed write locks. Run the Protocol `post-genesis` verifier before any
customer-write or mint authorization.

The live smoke gate must prove fresh EVM and BLS vault recovery, the complete
zkPassport-to-Sepolia-to-validator-to-Chia identity path, two-of-three
validator enforcement, replay resistance, retired-coordinate rejection, and
Alpha/Beta isolation. Payment ownership, Stripe, purchase, presale, settlement,
customer writes, and minting remain disabled until their own approved gates.

## Abort and evidence rules

Stop on any ref, commit, tag-object, checksum, manifest, reviewer, signer,
funding, contract-code, confirmation, validator, local-node, write-flag,
output-directory, or consumer-pin mismatch. Also stop on a fallback node,
non-loopback listener, stale or reused state, ambiguous response, unexpected
ceremony row, or unexpected chain activity.

Preserve originals and record only non-secret hashes, public fingerprints,
timestamps, health receipts, and vault references. Never copy private keys,
mnemonics, seeds, bearer tokens, invitation material, claim values, session
secrets, unsigned bundles, identity documents, or provider credentials into a
repository, manifest, chat, or public evidence packet.
