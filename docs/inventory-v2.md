# Available inventory V2 (draft, inactive)

V1 reservation execution raises because its ordinary rail-is-valid helper lacks a subtotal argument and reserve-conditions cannot access its caller state. V2 passes the subtotal explicitly and inlines condition construction. Every historical puzzle source, compiled byte sequence and tree hash remains unchanged. The existing reserved V5 module commits the selected AVAILABLE hash and therefore supports either version without replacing V5.

PrimaryMintTermsV3.inventory_version and PrimaryPurchaseMintConfig.inventory_version accept only integer 1 or 2. Missing historical values remain 1. API publish metadata inventory_puzzle_version is explicit, retained in publish_context, and enters deterministic mint-output/bill validation. Unknown or coerced values reject. The shared inventory_terms_for_puzzle_hash helper recognizes only the full V1/V2 singleton puzzle built from exact governed terms and optional reservation; callers must still verify canonical coin records, lineage, owner, network and signed release coordinates. It does not authenticate a supplied coin by itself.

Reservation, timeout, failure release, extension, native/Stripe/Base delivery, batch delivery and Stripe voucher delivery use the same selected terms. Recovery derives that selection from the retained original coin commitment and still compares exact original spends. Cross-version release and unrecognized hashes reject. A V1 timeout returns V1; changing a Python flag cannot upgrade an existing coin. Existing V1 AVAILABLE assets remain affected and must not be advertised as usable. No migration transaction is supplied.

Draft12 adds the portal's independent V1/V2 inventory curry builder and cross-language fixtures for deed, proposal and governance commitments. Correction to the prior handoff: the old portal constructed the historical 16-argument purchase delegate V2, not available-inventory V1. Its pure fixture path is preserved. New purchase publication now requires explicit inventory V2 at both the portal runner and authoritative API; historical records remain readable and unchanged.

For explicit V2, primary_purchase_usd_amount_minor means base price. The protocol adds ceil(base * 100 / 10000) once. For example, base 101 minor units has a 2-minor-unit fee and subtotal 103. New V2 uses the same V3 provider ID and canonical P2_VAULT module as purchase reservation/validation. Historical price/provider interpretation is not rewritten.

Activation requires a new signed artifact with the optional inventoryActivation extension. The extension binds schema solslot.inventory-activation.v1, environment (staging-alpha or production-alpha), testnet11, ceremonyId as deploymentId, inventoryVersion 2, adapterVersion 1, exact availableModuleHash and reservedModuleHash, all nine sourceShas, and a nonzero reviewEvidenceSha256. These bytes enter the existing canonical artifact hash and committee signatures. The old RC23 puzzleHashes and genesisPlan projections remain unchanged. The API additionally matches the runtime environment; the portal matches its explicit runtimeEnvironment. Missing/mismatched evidence disables new mint preparation. A review digest is a signed reference, not an independent review performed by the validator.

No artifact has been activated here. A new coordinated source release, fresh reviewed activation evidence, new artifact hash/signatures, governed V2 Testnet inventory and Hiram's concrete ActionEnvelope approval remain required. Existing signed artifacts must never be edited in place or implicitly upgraded.

The API's service-token-protected POST /protocol/native-purchases/inventory/resume-timeout accepts purchaseId only. It prepares each outstanding reserved input separately, requires the configured primary node, checks source creation, deployment treasury/validators, canonical ancestor time and a stable tip, then uses the existing bounded fee submitter. Full funded bytes and input/fee bindings are committed before dispatch. Restart/retry replays exactly those bytes; lease expiry never frees inventory. A partial external timeout can be reconciled while the remaining items advance. Only complete three-confirmation canonical successor evidence atomically marks the purchase RELEASED. The observer-only reconcile-timeout endpoint remains available.

Timeout dispatch is request-driven; no background worker is enabled. Ambiguous/rejected transactions retain PREPARED state and fee exclusions. Fees remain conservatively excluded even after an external release; fee-coin reuse requires a separately reviewed lifecycle. Never-confirmed reservations remain held. These backend paths still require customer-flow and deployed outcome verification.

Tests execute all four rails through reserve → timeout → fresh reservation, compare exact outputs and timelock conditions, verify synthetic BLS quorum signatures with a deliberately local domain, reject stale signature replay and malformed inputs, and exercise both versions in existing settlement and recovery controls. These are offline protocol checks, not customer Testnet confirmations, payments, receipts or device outcomes.
